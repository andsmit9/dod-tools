  **The game's own configs set cvars the pipeline assumed it owned (2026-08-26, `5a3c7a5`).** The verified capture ran with no `mirv_fov` or `r_decals` in the app's init commands — but `config.cfg` ends with `exec movie.cfg`, and that file carries `mirv_fov "105"` and `r_decals "0"`. So the on-screen cone was sized for the default FOV 90 (~55 degrees) while the engine rendered at 105 (~62 degrees). It passed regardless — occlusion carries the decision, and the wider cone drops only 228 of 4,289 camera-safe candidates on that demo — but the assumption was wrong and invisible, which is this feature's signature failure. `patch::cfg_scan` follows the exec chain from the configs the engine runs on its own and reports what they set; FOV now resolves init commands → executed config → configured default. `r_decals` is deliberately *not* adopted the same way, since that same file sets it to 0 and the pipeline's own pin runs after the config anyway. Binds and aliases are not counted as settings — `bind "F7" "r_decals 4000"` is in that config, and the cvar there is a payload, not an execution. **The scanner is strictly read-only: nothing in this app writes, edits, moves or removes a config file.** `native/src/bin/check_cfgs` reports a folder; the Capture Config pane banners it above Init Commands.

  **Init commands that override a config (2026-08-26, `6dca217`).** Init commands run after the engine loads its configs, so where both name the same cvar the init command wins — which is the point of typing one, but it also means a config line the user set deliberately stops applying with nothing to say so. The scanner now records *every* assignment rather than only the cvars the pipeline reads, since most configs never mention `r_decals` and the collisions that surprise people are the ones nobody thought to watch for. An assignment is a cvar-shaped name with exactly one argument, which keeps `+mlook`, bare commands and `mirv_fov handleZoom enabled 1` out alongside the binds and aliases. The check runs against the commands a capture would really apply — `builder::final_init_commands` is extracted so the app's own additions count too, which on the real folder catches `mirv_movie_fps 120` displacing `movie.cfg`'s 300. That also settles the seeded defaults: `r_decals 256` and `mirv_fov 90` can stay, because a new user now sees exactly what they displace.

  **Commands that never apply (2026-08-26, `b356d9d`).** `final_init_commands` puts the user's entries first and the pipeline's own after them, and the last one wins — so `mirv_movie_fps 500` typed by hand is dead on arrival against the `mirv_movie_fps <capture_fps>` appended a few entries later, with both lines visible and nothing to separate them. `cfg_scan::self_overrides` reports those, naming the setting that owns the value (editing the line cannot win, so pointing at the line would be useless advice). Commands that never apply are dropped from the config-override list rather than reported twice with opposite implications.

  **Custom commands, and the one that breaks the feature (2026-08-26, `c670d95`).** Custom commands are scheduled into playback, so they run after the game's configs *and* after the init commands — the last word on anything they set, and the only place a cvar changes partway through a capture. One case is not merely surprising: **`r_decals` scheduled mid-demo breaks the flush.** The cvar bounds how far the decal ring may travel before it wraps and evicts nothing, so lowering it during playback strands every decal above the new limit for the rest of the demo, while the capture completes and looks plausible. `cfg_scan::MID_DEMO_HAZARDS` names it, and the banner gives it its own section, first, saying to set the ring once in Init Commands instead. The pipeline has never scheduled `r_decals` itself and has a test saying so — nothing stopped a person doing it. Also deduplicated the override list to one row per cvar: typing a value the app also appends produced two rows with the identical consequence.

  **The camera test was judging the wrong point (2026-08-27, `b80eec3`) — found by raising `r_decals` to 4096.** Grids of flush decals appeared on walls in plain view in two takes, while the log reported zero on-camera frames. `R_DecalShoot` does not draw at the coordinate it is given; it projects onto the nearest surface. So a coordinate inside a wall passes "is it in shot with nothing solid in the way" *perfectly, from every camera, always* — it is occluded by the very surface it renders on. The filter therefore did not miss those candidates, it **preferred** them: the deeper inside a wall, the safer they scored. ## Sprint Takeaways & Architectural Rules
* **Standalone CLI Portability:** Strictly avoid dynamic disk-based localization lookups for headless binaries (`preview_cli`). Hardcoded literals prevent silent failures on target machines missing dictionary files.
* **Drag-and-Drop Tokenization:** Windows Terminal and PowerShell format drag-and-drop paths. `stdin` parsers must explicitly strip the `& ` evaluation operator and handle single (`'`) and double (`"`) quote wrapping to prevent path fragmentation.
* **Immediate-Mode UI (egui) Consolidation:** Never silo shared data types (e.g., `.dem` queues) across separate UI tabs. Use state-driven UI swaps (e.g., `CaptureMode` toggle) within a unified workspace. Always wrap vertically expanding configuration panels in `egui::ScrollArea::vertical().id_salt(...)` to prevent off-screen clipping.
* **Egui Ownership Safety:** Chaining builder methods that consume `self` (like `Response::on_hover_text`) triggers `E0382` errors. Declare the response as mutable and reassign it before evaluating `.clicked()`.
* **AI Git Hygiene:** Always audit `git show --name-only HEAD` before pushing. Autonomous IDE agents can hallucinate commit messages and silently contaminate unrelated files.
