### ✅ Unify the three independent, disagreeing capture disk-space gates (branch `fix/capture-disk-space-gates`, scoped 2026-08-23, fixed 2026-08-23)
Full writeup was Section 1, Item 2 of `docs/capture-render-ux-audit.md` — now fixed, see that doc's status header for which of its other findings are still open.

**The problem**: three separate, non-shared implementations of "is there enough disk space for this capture batch," which can disagree with each other:
1. **JS pre-flight** — `computeRequiredCaptureBytes` (`desktop-studio/src/capture_pane.js:63-121`), decides whether the Start button is enabled.
2. **Rust AOT allocation** — `allocate_blocks_first_fit_decreasing` + `block_estimates` (`native/src/patch/builder.rs:500-520`), snapshots free space once per drive at batch-build time and routes each block.
3. **Rust pre-launch abort** — `capture_engine.rs` (~line 397, confirmed still present), re-queries disk space with its own separate `sysinfo` call right before spawning HLAE and hard-aborts if the *primary* export dir alone has under a hardcoded 15GB free — regardless of what #2 already decided about the whole drive pool.

Only #3 re-checks space at the moment it actually matters (immediately before HLAE launches), but it's the narrowest of the three (single primary drive only). A batch can pass #1 and #2, then hard-abort seconds later from #3 — or the reverse, where #3 passes while #2 silently ran out of room on a secondary drive earlier in the pipeline.

**Proposed fix (from the audit)**: delete `capture_engine.rs`'s standalone 15GB check entirely; have `build_batch_queue` return the final per-drive headroom it already computed, so the pre-launch step re-validates *those* same numbers instead of computing a third, narrower answer. The JS pre-flight estimate doesn't need bit-for-bit parity with the Rust allocator (it's only ever a UX guard), but ideally keys off shared constants rather than an independent literal.

**Why this one, not the audit's other 8 findings**: flagged as the highest real-world-impact item — a correctness/reliability issue that can actually surface during real capture batches, not just a UX-polish or code-cleanup item (unlike most of the other 8 findings in the same doc, which remain untouched/available for a future pass). Low risk to fix: disk-space bookkeeping only, doesn't touch frame injection, the Cbuf limit, or process lifecycle — no CLAUDE.md guardrail directly implicated.

**Fixed, per the proposed-fix shape above**: `capture_engine.rs`'s standalone `sysinfo`-based 15GB primary-dir check is gone. `build_batch_queue` (`native/src/patch/builder.rs`) now returns `(Vec<PatchJob>, Vec<(PathBuf, u64)>)` — the second element is the final post-allocation headroom for every drive the batch actually touches: every drive that got at least one capture block routed to it (`utilized_drives`), plus drive 0 unconditionally, since the primer + each job's demo file always land on `capture_directories.first()` regardless of block routing. `spawn_capture_engine` takes that vector as a new parameter and its pre-launch check is now just a loop comparing each entry against the threshold — re-validating the exact numbers #2 already computed instead of recomputing a third, narrower answer via a fresh `sysinfo` call scoped to the primary dir alone. The two previously-independent 15GB literals (`builder.rs`'s `FAILOVER_THRESHOLD` and `capture_engine.rs`'s inline constant) are now one `pub const MIN_DRIVE_HEADROOM_BYTES` in `native/src/sys/disk.rs`, next to the `get_available_bytes`/`diagnose_path` functions that already do the per-drive disk querying. `capture_manager.rs` threads the returned headroom vector from `build_batch_queue` straight into `spawn_capture_engine`. JS pre-flight (`computeRequiredCaptureBytes`) left untouched, per the audit's own scoping — it's a UX guard only and never had an independent threshold literal to unify.

Updated all call sites for `build_batch_queue`'s new return shape (`builder.rs` unit tests, `native/src/bin/check_ticks.rs`, `native/src/bin/test_builder.rs`). `cargo build --workspace` and `cargo test --workspace --no-fail-fast` both clean — 27/27 in `native`'s own suite (including all pre-existing `patch::builder` tests), zero failures anywhere in the workspace.

Not done, deliberately out of scope per the audit's own "(c) Proposed fix" note: true cross-language parity between the JS estimate and the Rust allocator's merge-billing algorithm — flagged there as "real work" the JS-only UX guard doesn't strictly need.

*(Follow-up gaps found while live-testing the fix above — the drive-headroom threshold split, the hl.exe-install-drive check, the patched-demo persistence model, and the stale Capture Output footer — are now tracked as GitHub Issues: [#8](https://github.com/ccoventry/dod-tools/issues/8), [#11](https://github.com/ccoventry/dod-tools/issues/11), [#12](https://github.com/ccoventry/dod-tools/issues/12), [#13](https://github.com/ccoventry/dod-tools/issues/13).)*

### ✅ Disk-space checks trusted a mount-point prefix match with no check the actual path was usable — affects real capture/render drive allocation, not just the UI (found + fixed 2026-08-23)
User caught this testing the Capture Output yellow-warning feature from earlier tonight: added one valid Capture Output path, then appended `|` to the end and blurred. The warning banner correctly flagged the path as `malformed` (the new `diagnose_capture_output_paths` code working right), but the footer's "Capture Output Free" number didn't change at all, and Start Capture Batch stayed enabled — user correctly guessed it might be "evaluating the drive itself and not the path." Confirmed: `get_available_bytes` (`native/src/sys/disk.rs`) never checked whether the requested path actually resolves to anything — it just string-prefix-matches the path against known disk mount points (`"c:/real/folder|garbage".starts_with("c:/")` → true) and returns that whole drive's total free space if any prefix matches, regardless of what comes after. A malformed suffix like `|` doesn't break the prefix match at all, so the function happily reported real C: drive space for a path that can never actually be written to.

This isn't just a UI-preview bug — `get_available_bytes` is the same function `native/src/patch/builder.rs` uses for **real capture drive-allocation routing** (`build_batch_queue`'s bin-packing) and `native/src/hlcr/renderer.rs` uses for **real render JIT export routing**. A malformed-but-prefix-matching configured path could have been silently treated as a valid allocation target in an actual capture/render batch, not just in this warning banner. **Fixed**: `get_available_bytes` now calls the same `diagnose_path` used by the Capture Output diagnostics, and rejects (`u64::MAX`, same "excluded" sentinel as no mount match) any path classified `Malformed`/`NotAbsolute`/`NotADirectory` before ever trusting the mount-point match — a `NotFound` path still passes through unchanged, since many capture/render output folders are legitimately auto-created at write time and "doesn't exist yet" alone isn't disqualifying. The check runs once per the existing 2-second TTL cache refresh (not on every call), so it doesn't add extra per-call cost to a function used in hot allocation paths. **Re-verified live (2026-08-23)**: pipe-suffixed path → 0.0 GB free, red blocking error; removed the pipe → back to 1019.7 GB, no warning. Fully resolved.

**Follow-up, same session, user-requested**: fixing the above surfaced a second, smaller inconsistency — a well-formed path whose parent drive is real but the leaf folder doesn't exist yet (e.g. `...\02_HLAE_Rawww`, a typo'd-but-plausible folder) still got listed in the yellow "won't be used" warning even though `get_available_bytes`/the footer already correctly counted it as usable (not-yet-created is fine, per the fix above) — two signals disagreeing about the same single entry. Fixed by making `diagnose_capture_output_paths` return a `usable: bool` computed via the *same* `get_available_bytes` call the footer uses, instead of deriving a second opinion from `status` alone; the frontend's problem-filter now keys off `usable`, not raw status. **Also added, per user request**: a calm blue informational note (distinct from the yellow/red warnings) for exactly this case — "`\"path\"` doesn't exist yet — it'll be created when the capture starts" — since silently treating it as fully fine risked masking a genuine typo of an *intended* existing folder. Verified live: blue note shown correctly, footer still reads the real free-space total.

### ✅ Render-recovery prompt fired on every F5 reload during an active render, even though nothing was interrupted (found + fixed 2026-08-23)
Found incidentally while retesting Section 5's NVENC concurrency warning: pressed F5 mid-render (to double check a toast), and the "Render Batch Interrupted" recovery modal popped up — not because anything crashed, but because `check_render_autosave` (`render_manager.rs:651`) only ever checked whether `.render_autosave.json` exists on disk, with no idea whether a render is actually still running in this process. F5 reloads the WebView only, not the Rust backend — the render job the user was watching kept running the whole time, untouched. The autosave file is written continuously as each job finishes (not just at batch end), so it's legitimately present during a real, ongoing render, which is exactly when this false-positive prompt fired. Clicking "Discard" didn't stop anything either (it only deletes that file; the detached render task doesn't check it), and the prompt came back on a third F5 because the next job finishing simply rewrote the file. **Fixed**: `check_render_autosave` now takes `state: tauri::State<'_, RenderManager>` and returns `None` immediately if `state.is_rendering.load(Ordering::SeqCst)` is true — a render actually running in this process is never something to "recover," it's just still going. **Re-verified live (2026-08-23)**: started a render batch, pressed F5 mid-render — no recovery prompt appeared, and Render Studio's job table still showed both jobs actively rendering after the reload. Fully resolved.

### ✅ Closing the app while an Init/Custom Command field still had focus silently dropped the edit (found + fixed 2026-08-23, confirming a risk the testing checklist had flagged but not yet verified)
`capture-render-quick-wins-testing-checklist.md`'s Section 4 specifically called this out as an open question when it was written: `list_editor.js` (backing Capture Output, Render Folders, Render Studio's Export Drives, Init Commands, and Custom Commands) updates its in-memory item array on every keystroke (`'input'`), but only triggers the actual `persistAppSettings()` disk write on `'change'` (blur/Enter) — deliberately, to avoid a full settings write per character while composing a value. ### ✅ Capture Output's "unusable pool" warning gave the same generic message for an empty list and for a list full of invalid paths (found + fixed 2026-08-23)
Found while testing Section 3 of `capture-render-quick-wins-testing-checklist.md`, which turned out to reference a UI field ("Media Output Directory") removed back on 2026-08-17 — the real equivalent today is the mandatory "Capture Output" list. While confirming that, added an entry of just `"a"` and got the same "No Capture Output directories configured" message as an empty list — misleading, since a directory *was* configured, it just didn't resolve to anything usable. Root cause: `refreshLaunchGuard` (`capture_pane.js`) computed `noDrivesConfigured = effectiveDrivePool.length === 0 || availableBytes === 0` — one merged condition for two different problems. **Fixed** with a real per-path diagnosis, not a guess: added `native::sys::disk::diagnose_path` (gated non-wasm, mirrors `get_available_bytes`'s cfg pattern) classifying each path as `Ok` / `NotAbsolute` (no drive letter or UNC root — Rust's `Path::is_absolute()`) / `Malformed` (OS rejected the syntax — `ERROR_INVALID_NAME`/`ERROR_INVALID_PARAMETER`/`ERROR_BAD_PATHNAME` from `fs::metadata`'s raw OS error) / `NotFound` (well-formed, doesn't exist, or an unmounted drive letter) / `NotADirectory` (exists, but is a file). New `diagnose_capture_output_paths` Tauri command surfaces this per-path; the frontend only calls it once the aggregate sum is already known to be zero (not on every keystroke — a per-path OS stat isn't as cheap as the existing TTL-cached aggregate sum). Verified each category individually: `Z:\` (unmounted drive) → `not_found`; `"a"`/`"b"`/`"c"` (no drive root) → `not_absolute`, joined into one message when multiple entries have problems.

Also chased what looked like a second, much scarier bug on the same list — a long mix of invalid paths (`C:\test|pipe`, `C:\test"quote`, `C:\test<>folder`, etc.) stopped showing any warning at all and let Start Capture Batch go enabled, surviving a full `tauri dev` restart (ruling out HMR staleness). The aggregate gate is deliberately "does *any* configured drive have room" — one valid entry correctly clears the warning for the whole pool, by design, since real usage means several real drives configured at once. Confirmed the per-path diagnostic fix above is unaffected by this — it was never broken, just correctly not firing once a genuinely usable drive was mixed into the pool.

**Follow-up UX pass, same session, user-requested**: that "at least one drive usable" case was silently swallowing the bad entries' problems entirely — nothing told you they'd be skipped. Added a non-blocking **yellow** banner (`#ffa726`) for exactly that case (`hasPartialProblems` in `refreshLaunchGuard`), reusing the same per-path diagnostics already fetched for the red case rather than a second IPC round-trip. Also capped the reason list at 3 entries (`+N more` tail) and switched from a semicolon-joined sentence to a point-form bullet list (`white-space: pre-line` on `#disk-space-warning-banner`, still plain `textContent` throughout — no `innerHTML`, so user-typed path text can't be interpreted as markup) after the first version proved to be an unreadable wall of text with a long invalid list. ### ✅ "Open Take Folder"/"Open Output" silently opened the wrong folder on a missing path (found + fixed 2026-08-23, testing `capture-render-quick-wins-testing-checklist.md`)
Found while running Section 1's edge case ("delete/rename a take folder, click Open Take Folder — should toast an error, not crash"). ### ⚠️ Rendered audio was broken two different ways — both found 2026-08-22, mid `MIN_TAKE_SEPARATION_SECONDS` calibration testing
Started as one symptom ("rendered audio sounds awful, like static/a helicopter") that turned out to be two independent, stacked bugs. Raw `sound.wav` in the take folder was correct throughout both — confirms the corruption was always introduced during the render/mux step, never at capture.

- [x] **Bug 1 — Render Studio's FPS has no connection to the FPS a take was actually captured at, causing sped-up video.** User captured at 120fps but Render Studio's Codec/FPS panel still had `300` (its last-used value from earlier testing, per the VirtualDub-style per-job settings model — see the 2026-08-18 "Render Studio: per-job settings" entry in Completed Tasks); render log confirmed `fps=300` on every batch that night. Root cause: `renderer.rs:31`'s `config.fps` feeds `-framerate` *before* `-i hudcolor/%05d.bmp` — that flag tells ffmpeg how to interpret the BMP sequence's timing (`computed video duration = frame_count / declared_fps`), so a wrong value produces a wrong computed duration (2.5x too fast at 300 vs. an actual 120fps capture), and `-shortest` then trims output against that wrong duration. No error surfaced; render reports success either way. **There is still no source of truth anywhere linking a take folder to its actual capture FPS** — `config.fps` is the only place `hlcr/renderer.rs` gets `fps` from, entirely independent of Capture Studio's own Capture FPS setting at capture time. User confirmed re-rendering with FPS manually matched (120) fixed the sped-up video — verified via `ffprobe`, rendered duration now matches the take's own `sound.wav` duration exactly (14.83s both). **Diagnosed and manually worked around 2026-08-22; the missing source of truth was added 2026-08-27.** `native/src/hlcr/take_meta.rs` records the batch's `mirv_movie_fps` in a `dodtools_take.json` in each take's own block folder, and `run_render_job` reads it and logs `[render-fps-mismatch]` naming both rates, the resulting speed factor and its direction, and the value to set instead.

**Per take, not per session** — the first cut wrote one file per session folder and the user caught the hole in it immediately by asking what happens when highlights are captured at one FPS and something else at another. Different batches do get different session folders (`session_YYYYMMDD_HHMMSS`, generated per dispatch), so a session-level file is correct for that case; and FPS cannot vary *within* a batch, since `capture_fps` is a single `PatcherConfig` value and `mirv_movie_fps` is set once in the init commands. What it is not correct for is a take being **moved**: a session-level file describes a location, so a take dragged into another session's folder silently inherits that session's settings — this exact bug, one level up. A per-take file travels with the take.

Writing into the block folder collides with `take_folder_has_content`, which decides a take was captured by asking whether its folder is non-empty — an empty block plus our file would report a capture that never happened. Handled by `take_meta::is_metadata`, which that check now consults, rather than by writing somewhere else and hoping nobody re-runs verification on an old session later. It is still written after verification and only for blocks that landed, but that ordering is now belt-and-braces rather than the only thing holding it up.

Deliberately **advisory, option (b) rather than (a)**: the renderer states the disagreement and renders exactly what was asked. A take folder can be moved, copied or hand-assembled, and a renderer that silently substituted a number found in a neighbouring file would be a worse surprise than the one it fixes. Takes captured before this exists have no file and produce no warning, which is the correct silence rather than a defect.

Worth recording as a near-miss: the first version sent the warning as a `RenderUpdate::Status`. `job.status` is a state field with a fixed vocabulary (`"Queued" | "Rendering" | "Finished" | "Error" | "Cancelled"`) that the scheduler's own transitions test against — `if job.status == "Rendering"` gates the Finished transition and `active_count` counts it — so a sentence in that field would have shown a paragraph where a status chip belongs and stranded any job that returned before `"Rendering"` overwrote it.
- [x] **Bug 2 — MP4 output used a PCM audio box (`ipcm`) that FFmpeg/VLC read fine but Vegas Pro can't, producing garbled/static audio independent of the FPS bug above.** Found after fixing Bug 1 didn't fix the audio — FPS-matched retest still sounded broken. Root-caused by direct comparison: the user's older working clips were all `.mov`/ProRes, never `.mp4`; every render since the 2026-08-18 "H.264 output was always `.mov`" fix (which made real `.mp4` output possible) shares the exact same `-c:a pcm_s16le` line (unchanged since `pcm_s16le` was originally ported straight from the user's own Python HLCR tool, `git bda4f7a`) — the only variable that changed was the container. Confirmed empirically, not just by inspection: remuxing the *exact same* PCM audio bytes (`ffmpeg -c copy`) into `.mov` instead of `.mp4` made ffmpeg auto-select the older, broadly-supported `sowt` tag instead of `ipcm`, and the user confirmed that `.mov` remux sounds correct in Vegas. MP4 has never had solid native support for raw PCM audio in the first place (audio-in-MP4 is conventionally AAC almost everywhere) — trying to force the `sowt` tag onto an MP4 output directly failed outright (`Tag sowt incompatible with output codec id 'ipcm'`), confirming this needs a real codec change, not a tag override. **Fixed**: `renderer.rs` now picks `-c:a aac -b:a 192k` for the MP4-outputting presets (h264_nvenc, libx264) and keeps `-c:a pcm_s16le` for the MOV-outputting ones (ProRes, DNxHD/alpha-HUD), decided in the same `file_ext` match so the two can't drift apart, mirroring the existing video-codec/extension pattern. Verified via a real render (h264_nvenc + AAC) — `ffprobe` confirms `aac (LC) (mp4a)`, standard/correct — **and the user confirmed the AAC test render plays back correctly in Vegas Pro.** Fully resolved.
